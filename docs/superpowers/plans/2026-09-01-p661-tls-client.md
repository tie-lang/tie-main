## Requirements summary

p.6.6.1 交付纯 tie 的 TLS 1.3 + 1.2 客户端（ext/tls）：完成握手、记录层加解密、
X.509 证书链校验，为 p.6.6.2 httpc 与后续 LLM/Web 框架提供字节级安全信道底座。
**前置里程碑：p.6.4 原语全面 tie 化（全部 10 项）先行完成**——p.6.6.1 依赖的
字节级网络 IO（net\_tcp\_recv\_bytes / net\_tcp\_send\_bytes）由 p.6.4.5 网络 tie 化落地，
不再新建 Rust 桥。

* AC-1 `compiler/`: net\_tcp\_recv\_bytes / net\_tcp\_send\_bytes 编译为内联 IR（零 Rust 桥）。

* AC-4 `ext/tls/tls1_3.tie`: 与 openssl s\_server 完成真实握手 + 应用数据回环（AES-128-GCM 套件）。

* AC-6 `ext/tls/tls1_2.tie`: 对仅支持 TLS 1.2 的服务器握手成功（ECDHE + AES-128-GCM）。

* AC-7 `ext/tls/tls.tie`: 统一入口 connect/send/recv/close 全流程 demo PASS。

## RALPLAN-DR

### Principles

* 跟随 baseline「最小代码」：每个模块先跑通最简套件，不预铺扩展点。

* 跟随 spec 的 In scope：只做客户端、只做 x25519 主 + secp256r1 可选、只做内置 CA。

* 外科手术式改动：编译器改动只在既有原语登记处追加分支，不动既有原语行为。

* **p.6.4 地基优先**：字节网络 IO 由 p.6.4.5 落地，p.6.6.1 不重复造轮子。

### Decision drivers

* 编译器自举风险（tiec 任何行为漂移会破坏全仓）。

* 密码学正确性（权威向量对齐是硬门槛）。

* 网络可测性（openssl 3.6.1 本机可用，不依赖外网）。

* **排期**：p.6.4 全部 10 项先做（用户已确认），p.6.6.1 依赖其字节 IO 基座。

### Viable options

**Option A: p.6.4 前置 + 编译器内联 IR 原语 + 纯 tie TLS（推荐）**

* 实现思路：先完成 p.6.4 全部 10 项 tie 化（含 p.6.4.5 网络 net\_\* 重写为 Winsock2
  extern/纯 tie，提供字节级 recv/send）；随后 net\_tcp\_recv\_bytes/send\_bytes 直接落在
  std/net 层，TLS 全用 tie 写。

* 改动文件：p.6.4 各子项对应 compiler/backend/*、compiler/interp/*、std/*；
  p.6.6.1 时 ext/tls/*（纯 tie）。

* Pros: 零 Rust 桥（与 p.6.4 方向一致）；TLS 逻辑全在 tie 可审计；字节 IO 由
  p.6.4.5 一并系统性解决（不只 TLS 受益，httpc/db 皆受益）。

* Cons: 前置里程碑体量大（10 项），p.6.6.1 实际启动时间后移；p.6.4 每一步仍需
  探针 + 自举验证。

**Option B: ext 内 unsafe extern 直调 Winsock（已否决）**

* 实现思路：不动编译器，在 ext/tls 内 `unsafe extern fn recv/send` 直连 ws2\_32。

* Pros: 零编译器改动；ecdsa 已有同型先例。

* Cons: 仅 Windows；字节表↔缓冲 ABI 需手拼；与 p.6.4 原语 tie 化方向相悖；
  用户已在策略对齐阶段选「编译器新原语（p.6.4.5 承接）」。

**Option C: 扩展 Rust 桥 tie\_interp.lib（已否决）**

* 实现思路：改 tie-interp Rust 工程加 tie\_net\_tcp\_recv\_bytes 符号后重建 .lib。

* Cons: 与 p.6.4「消除 Rust 桥原语」总目标相反；tie\_interp.lib 是 prebuilt 产物，
  改 Rust 侧需额外工程链路；invalidate。

**Step 1 — 字节网络原语验收（AC-1，依赖 p.6.4.5）**
12\. 探针 `tests/language/std_net_bytes.tie`：本地回环 TCP（net.tcp\_listen/accept 服务端
\+ 客户端）bytes 往返：发送 \[0..255] 全字节表，recv\_bytes 逐字节一致。
13\. 自举：scripts/selfhost-gate.ps1 重建 tiec.exe，验证 tiec2==tiec3。

**Step 2 — DER + GCM + AEAD（AC-2/AC-3）**
14\. `ext/tls/der.tie` — DER TLV 解析器：长度编码（短/长形式）、tag 分类、
序列遍历 API（参照 std/json 的平行表节点风格，节点 id 为下标）。
15\. `ext/tls/gcm.tie` — GHASH（GF(2^128)）+ GCTR + seal/open；依赖 ext/aes 的轮函数
（AES-128/256，E\_K 块加密；ext/aes 现只暴露 ECB 接口，可复用 encrypt\_ecb 单块）。
16\. `ext/tls/aead.tie` — ChaCha20-Poly1305 AEAD：组合 ext/chacha20 与 std/poly1305
（RFC 8439 构造：poly1305 key = chacha20 前 32 字节块）。
17\. 探针 `tests/tls_probe/der_probe.tie`（已知证书字段断言）、
`tests/tls_probe/gcm_probe.tie`（RFC 8452 §A.1/A.3 向量）、
`tests/tls_probe/chacha_poly_probe.tie`（RFC 8439 §2.8.2 向量）。

**Step 3 — TLS 1.3 握手 + 记录层（AC-4）**
18\. `ext/tls/tls1_3.tie` — ClientHello（supported\_versions 0x0304、key\_share、signature
algorithms、supported\_groups）+ ServerHello/EncryptedExtensions/Certificate/
CertificateVerify/Finished 解析（消息解析基于 der 长整/长度工具）。
19\. HKDF 子密钥派生：std/hkdf.derive 为 hex IO —— tls1\_3 内部加 hex↔table 适配层
（复用 ext/ecdsa 的 hex\_to\_bytes/bytes\_to\_hex 工具，或抽到 ext/tls/tool.tie）。
20\. 记录层：类型/版本/长度头 + AEAD seal/open（以 type+version+len 作 AAD）。
21\. 探针/验收 `tests/tls_probe/tls13_hello.tie`：对 127.0.0.1 openssl s\_server 完成
握手（-tls1\_3 -cipher AES128-GCM-SHA256），exchange "ping"/"pong"，断言应用数据一致。

**Step 4 — X.509 + 链校验 + 内置 CA（AC-5）**
22\. `ext/tls/x509.tie` — 证书结构解析（tbsCertificate/有效期/签名算法/SPKI/RDN/SAN），
指纹（sha256）。
23\. `ext/tls/chain.tie` — 链构建（逐级 issuer → trust anchor）+ 签名校验
（RSA PKCS#1v1.5/PSS 用 std/bigint.powmod；ECDSA P-256 复用 ext/ecdsa.verify）+
有效期 + 主机名匹配（SAN dNSName / CN）。
24\. `ext/tls/ca.tie` — 内置常见根 CA 表（PEM/SPKI 提取：DigiCert/GlobalSign/ISRG/
Let's Encrypt/Cloudflare 等 ≈10 根），set\_ca 可追加。
25\. 验收 `tests/tls_probe/tls_chain_probe.tie`：本地 openssl 自签链校验通过；
伪造/过期/主机名不符 → 被拒（改 SAN 探针、改 valid 窗口探针）。

**Step 5 — TLS 1.2 兼容（AC-6）**
26\. `ext/tls/tls1_2.tie` — ClientHello（0x0303，cipher suites）+ ServerHello/
Certificate/ServerKeyExchange（ECDHE 参数）/Finished 解析；PRF-SHA256 密钥派生。
27\. 记录层：版本 0x0303 + AEAD（AAD 无 type 字节，unused type 0x1603）。
28\. 验收 `tests/tls_probe/tls12_hello.tie`：openssl s\_server -tls1\_2 握手成功。

**Step 6 — 统一入口 + 文档（AC-7）**
29\. `ext/tls/tls.tie` — connect() 依 supported\_versions 协商 1.3/1.2；Session 结构
（socket 句柄 + 套件 + 密钥状态 + 读缓冲平行表）。
30\. 文档：ext/tls 各文件头注释（双语规格 `doc` 风格同 argon2/scrypt）+ README/CHANGELOG
（p.6.6.1 条目，双语，英文 commit message）。

## Risks & mitigations

| Risk                                                                   | Mitigation                                                                 |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| p.6.4 全部 10 项体量大、周期长，p.6.6.1 启动后移                                      | 每子项独立 commit + 探针；AC-0 硬门槛（零 tie\_interp.lib 链接+零回归）才放行；按用户「一个小任务提交一次」节奏推进 |
| 编译器改造 5 处 + 自举破坏现有自举链                                                  | 每步归零探针 + 自举 tiec2==tiec3 作为硬门槛，失败即回滚该步 commit                              |
| recv 内联 IR 表组装 O(n²)（byte\_read 同族曾爆内存）                                | 先分配 cap 一次性缓冲再逐字节 zext 存储（照抄 2557-2630 范式），禁止逐元素 push                      |
| 密码学实现与权威向量不符                                                           | GCM/HKDF/ChaCha-Poly 全部用 RFC 向量硬编码断言后才会进入握手集成                              |
| openssl 3.6.1 新套件命名差异（AES128-GCM-SHA256 vs TLS\_AES\_128\_GCM\_SHA256） | 握手探针同时断言 ClientHello 字节序列（golden），不只依赖对端成功                                 |
| 链校验内置 CA 表覆盖面不足                                                        | 表可追加（set\_ca）；默认覆盖主流站点；验证用本地自签链（可控），不赌外网                                   |
| tie string 不可承载 ≥0x80：X.509 解析全字节表                                     | 全链路 table<i64>；hex 仅在内部工具适配层出现（复用 ecdsa 工具）                                |

## Pre-mortem（deliberate）

1. **Scenario**: p.6.4 网络重写（p.6.4.5）的字节表句柄组装错（cap/len/data 布局不对）
   → 所有使用字节网络 IO 的程序运行 AV。
   **Trigger**: 探针运行 0xC0000005。
   **Mitigation**: 先写往返探针断言 byte 相同 + len/cap 正确，再进 TLS；句柄布局照抄
   tig\_byte\_read 已工作代码，不新发明。
2. **Scenario**: 自举 tiec2!=tiec3（编译器改动引入输出漂移）。
   **Trigger**: selfhost-gate 失败。
   **Mitigation**: 每步单独 commit；失败即回滚该 commit 重做，不覆盖当前 tiec.exe
   基线，保留可工作的 tiec 副本。
3. **Scenario**: GCM 向量对齐花时间过长（AES 轮函数经 hex 中转细节错位）。
   **Trigger**: gcm\_probe 断言失败 > 该模块预算。
   **Mitigation**: 用已知 16 字节明文单块对照（E\_K 单块先验）；hex↔table 边界先单测。
4. **Scenario**: p.6.4 全量验收时部分项（如 unzip/untar\_gz）的基础解压实现与既有
   codec 库行为不一致。
   **Trigger**: 存档往返探针失败。
   **Mitigation**: 独立拆成子项 commit，与既有 codec 探针对比向量，局部回滚不影响整体。

## ADR

* **Decision**: p.6.4 全部 10 项原语 tie 化前置，随后编译器内联 IR 字节网络原语
  （Option A）+ 纯 tie TLS 1.3/1.2 客户端。

* **Drivers**: 零 Rust 桥（p.6.4 方向）；可审计；复用 byte\_\* 成熟先例；用户排期确认
  （p.6.4 先行）。

* **Alternatives considered**:

  * Option A（chosen）— p.6.4 前置 + 内联 IR 原语；已在采用。

  * Option B（rejected）— extern 直调 Winsock；仅 Windows、ABI 手拼、与 tie 化相悖。

  * Option C（rejected）— 扩展 Rust tie\_interp.lib；反 p.6.4 目标、需 Rust 工程链路。

* **Why chosen**: tiec 自举编译器是全仓地基，内联 IR 改动面受控且已有 byte\_\* 成功
  先例（零 Rust 依赖）；p.6.4.5 系统性解决网络字节 IO，TLS/httpc/db 共同受益；
  TLS 协议层留在纯 tie 便于探针验证与后续维护。

* **Consequences**: p.6.4 前置使 p.6.6 启动后移；编译器多处登记需同步（漏一处即编译
  失败，探针兜底）；recv/send winsock 链接依赖新增 g\_used\_wsock 标志；TLS 实现量与
  自举验证成本是 p.6.6.1 主要开销。
