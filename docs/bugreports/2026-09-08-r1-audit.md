## 二、编译器正确性

1. **【高·未修复·已 RCA】RCA-2：循环体 alloca 不提升**——深循环 + 批量局部变量致
   0xC00000FD 栈溢出（repro2_sort 冒泡 3000 字符串即触发）。五个边界化修复变体
   （全量/选择性提升 ± 零初始化、stacksave/stackrestore、原地零 store）全数证伪；
   正确路线 = 源码层「首读前必写」清理 → 全量提升 + 零初始化（r.1.1）。
2. **【高·未修复·同根】未初始化读是隐性契约**——编译器自身
   （tig_read_file/tig_write_file 块级表槽）与 std/ed25519/bigint 存在大量
   「alloca 槽首次 store 前被读、且读值参与控制流」的未初始化读，历史上依赖
   逐迭代动态栈分配运转；任何使槽位复用或显式归零的变换都会偏转控制流崩溃。
   与 1 同属 r.1.1 攻坚面。
3. **【中·新确认】table_coll_p2d IR 类型缺陷**——实测复现：opt 报
   `%N defined with type '{ i64, i64 }' but expected 'ptr'`（ptrtoint 把
   `{i64,i64}` 元组值当指针）。当前 tiec.exe 与旧不动点 tiec_ADA0CAB7_old.exe
   均复现 → 长期存在的 irgen/llvmgen 类型不匹配 bug，需 RCA（r.1.4）。
4. **【中】shift_neg_free 负例未拒**——应拒绝的移位越界/负自由场景编译成功
   （exit 0），语义检查缺一条规则（r.1.4）。
5. **【低·已缓解】ed25519 阶梯泄漏**——divrem/invmod 非 entry 表局部返回绑定
   孤儿泄漏（每 point_mul ~92MB）；缓解已发，根治依赖 r.1.1 的支配安全提升。
6. **【低·新发现】未支持指令静默降级**——`compiler/backend/llvmgen_inst.tie:955`：
   未支持指令落至 `line("; TODO op=...")` 占位注释后**继续链接**，不报错终止
   → 产物行为不可预测。应改为硬错误（r.1.4）。
7. **【低】dbg_fsp 测试过期**——见 §一；随 r.1.4 一并更新。

EN: RCA-2 (loop-body alloca hoist) and the latent read-before-write contract
remain the top correctness debt (r.1.1); the p2d ptr-vs-tuple IR defect and
shift_neg_free acceptance gap are newly confirmed as long-standing (r.1.4);
llvmgen silently continues on unsupported instructions (new finding, r.1.4).

## 三、性能（「解析/拼接/匹配路径无 O(n²)」铁律核查）

1. **【高·新发现·铁律违规】std/json 字符串与数字解析 O(n²)**：
   * `std/json.tie` parse_string（L289-375）：逐字符 `str_char` + `out = out + c`
     不可变拼接——长字符串值二次方复制；
   * parse_number（L203-284）：`digits = digits + c` 同模式。
   httpc / str.split/slice/join / LSP 侧均已字节化，唯独 json 漏网；应改
   `str_byte` 索引扫描 + string_builder（r.1.3）。
2. **【中】逐码点 str_char 全串扫描残留**——std/yaml（preprocess/strip_comment 等）、
   std/markdown（标题/表格判定等多处）仍按码点 `str_char` 逐位扫描；本运行时
   str_char 单次成本高（历史实测 ~360µs 量级）且 UTF-8 多字节定位退化。拼接侧已用
   string_builder，扫描侧待字节化（r.1.3 顺带评估）。
3. **【低】** compiler/lsp/protocol.tie 的 split_lines / parse_int_trim 逐字符 `+`
   拼接——仅作用于短帧头，可忽略。

EN: std/json still parses strings/numbers with per-character str_char plus
immutable concatenation — an O(n²) residual violating the project iron rule
(r.1.3); yaml/markdown retain per-codepoint scans (medium); protocol.tie's
short-header builders are negligible.

## 四、安全

1. **【高·新发现】TLS 证书链校验未接入连接路径**——`ext/tls/chain.tie:491`
   `pub func verify(ch, roots, host)`（逐级签名/有效期/根锚/主机名校验）已实现，
   但全仓库唯一调用方是工具 `ext/tls/ca.tie`；`tls.connect` → `finish13`/`finish12`
   （`ext/tls/tls.tie`）**全程不验证书、不验主机名** → 中间人持任意自签证书即可
   完成握手，https 流量可被劫持。修复：握手 Certificate 阶段解析链并调用
   chain.verify（r.1.2）。
2. **【高·新发现】TLS 密钥材料来自非加密安全 PRNG**——`ext/tls/tls1_3.tie`
   rand_bytes（L45-49）= `rnd.int(0,255)` 逐字节；`std/random.tie` 头部自声明
   「非加密安全，勿用于密码学/安全令牌场景」。用途包括 x25519 私钥、
   ClientHello random、session id；tls1_2 的 P-256 临时私钥（gen_p256_sk）同源
   → **会话密钥可预测**。修复：新增 CSPRNG 底座原语并切换密钥材料来源（r.1.2）。
3. **【低】** std/tsha1 等自研密码学无第三方审计（模块头已自声明）；CRC32/FNV
   非加密用途已在 std/crypto.tie 正确标注。

EN: two high-severity gaps — chain verification exists but is never called from
the connect path (MITM), and all TLS key material comes from a self-declared
non-cryptographic PRNG (predictable session keys). Both targeted by r.1.2
(CSPRNG base primitive + wiring chain.verify into the handshake).
