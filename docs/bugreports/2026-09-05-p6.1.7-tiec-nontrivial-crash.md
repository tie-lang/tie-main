# 缺陷报告 p.6.1.7：tiec 编译「非平凡程序」产出即崩（0xC0000005 / 0xC00000FD / 挂起）——代码生成产物级不稳定

> 报告日期：2026-09-05
> 组件：tiec 编译后端（LLVM IR 生成 / 优化 pass / 与运行期配对）
> 归属仓库：tie-main（本仓库）
> 复现仓库：tie-jcc-core（闭源，证据探针留存；本文给出独立于 jcc 的触发形态与证据矩阵）
> 编号：**p.6.1.7**（正确性模块 p.6.1，继已修复同族 p.6.1.4 / p.6.1.6 后）
> 严重度：高（阻断一切对非平凡程序的重新编译；新增复杂程序在本工具链下不可构建运行）
> 状态：未修复
>
> *English summary*: Compiling non-trivial tie programs (large functions, multi-module,
> table-heavy code such as dpbase pack assembly / engine / full jcc-pack) with every
> current tiec variant succeeds but produces executables that crash on startup or hang
> (0xC0000005 AV / 0xC00000FD stack overflow / no-output hang), across -O0..-O3 and
> release/debug runtime pairings; small programs and all pre-built binaries are unaffected.
> This is a codegen-level instability, not a data or logic issue, in the same family as the
> already-fixed p.6.1.4 (register allocation) and p.6.1.6 (str_char bounds).

## 一、现象

`tiec <非平凡程序>.tie -o out.exe`（exit 0，产物生成）后运行 `out.exe`：

* 立即 **0xC0000005**（Access Violation，无任何输出）；或
* 立即 **0xC00000FD**（栈溢出）；或
* **挂起**（CPU 持续占用、stdout 与落盘日志均无产出）。

触发面（全部实测命中）：

* 包含 dpcodec / zstd / pack 装配的小程序（load 现有包 → encode → 压缩）；
* 仅 `byte_read + pngde.to_gray` 的小程序；
* calc 引擎全量探针重编；
* jcc-pack（tools/jcc-pack/main.tie 全量，含 build/info/extract）。

对照（不触发，同编译器同行）：

* 仅 `json.parse_file`（378 KB 文件）；
* `httpc.get_bytes`（http 明文）+ PNG 解码 + struct 入表；
* `net` + `httpc` 明文 + `fs` 组合。

关键观察：

* **与优化等级无关**：-O0/-O1/-O2/-O3 全数复现（-O0 亦崩 → 非优化 pass 单一问题，或为更底层代码生成/链接问题，优化只是掩盖/偏置）。
* **与编译器变体无关**：09-02（tiec_new）、09-04（tiec80）、09-05 01:16（tiec_5F6CB9，记录不动点）、09-05 13:27（现版，引用计数插桩后）全部复现 → **非 09-05 引用计数插桩（p.6.10.3/4）引入的增量回归**，是正确性模块长期未根治的族系残留。
* **与运行期配对无关**：release（34916060 B，08-15）/ debug tie_interp.lib 全部复现。
* **预构建二进制不依赖环境变量**：env（TIE_INTERP_LIB/TIE_TRM_LITE_LIB）仅编译链接期生效，运行期不读 → 旧产物与当前产物差异仅来自编译器代码生成。

## 三、根因分析

* **非数据内容**：解码值全程正确（既探针 info 路径正常）、testsrc 小数据任意形态正常。
* **非逻辑错误**：同源码仅改变无关邻接代码，产物在「崩溃 / 挂起 / 正常」间翻转（1–5 号用例与 6–8 号用例形态差异即为此特征）→ **编译形态决定产物生死**。
* 家族溯源：已修复 p.6.1.4（大函数寄存器分配缺陷：跨模块全局访问器 + 交错多表 push + 循环内字符串累加）与 p.6.1.6（str_char 越界）同属「编译形态触发」；本次为新覆盖形态（大程序批量表分配 + 深循环 + 多模块），当时修复未覆盖。
* 疑点：长函数/循环内批量 `table_push`/`byte_write` 等生成的 LLVM IR 在寄存器分配或别名阶段出界（堆损坏特征：崩溃点对无关代码敏感）；-O0 仍崩提示也可能涉及 IR 生成（alloca/gep 布局）而非纯优化 pass。
* 附带隐患：p.6.10.3 / p.6.10.4 引用计数插桩后自举字节已变、**新 SHA 未记录核验**，编译器/运行时配对一致性未被确认——建议修复前先冻结并核验有效配对。

## 四、最小复现（独立于 jcc）

独立打点方式（在 tie-main 内即可完成）：

1. 取任意一个当前能编译运行的小程序（对照 6–8 形态）；
2. 为其加上一段「深层循环 + 批量表分配 + struct 字段读写」的代码（见下骨架）；
3. `--keep-ir` 保留 `.ll`，对比崩/不崩两形态的 IR 差异。

触发形态骨架（无 jcc 依赖，构造要点：长循环体 + 每轮建表 + 字段写回）：

```tie
type tie<logic>
// 触发形态骨架：长循环 + 逐轮建表 + struct 字段整体写回 + 字节表累积
struct Rec {
    var id: string = ""
    var items: table<i64> = []
}
func hammer(n: i64, tgt: table<Rec>) -> i64 {
    var k: i64 = 0
    while k < n {
        var tab = table_new_i64()
        var j: i64 = 0
        while j < 8 {
            table_push(tab, k * 31 + j)
            j = j + 1
        }
        var r = Rec()
        r.id = "r" + to_string(k)
        r.items = tab
        table_push(tgt, r)
        k = k + 1
    }
    return len(tgt)
}
func main() {
    var tgt: table<Rec> = []
    var n = hammer(100000, tgt)
    println("n=" + to_string(n))
}
```

> 说明：上骨架为「疑触点」形态示例；实测复现集合（§二 1–5）已可整体作回归输入，闭环后应以真实用例集（tie-jcc-core 闭源仓**可以提供最小化用例转出**）为准。

## 五、影响

* 阻断 tie 生态一切对 2026-09-02 前既有程序的重新编译（任何依赖 dp/zstd/pack/引擎等大库的程序）；
* 新增复杂程序（网络、打包、引擎、UI）在当前工具链下不可构建运行；
* 覆盖范围 = 本仓库所有消费者（tink 各语言桥为跨语言产物不涉及，但 tie 侧工具链与 std 集成均受影响）。

## 六、修复方向（供后端）

1. 建立「非平凡回归探针集」：将 §二 1–5 号用例纳入 tie-main 回归，防止修复后复发；
2. 用 `--keep-ir` / `--emit-ir` 抓崩溃程序 `.ll`，与正常对照 diff，定位坏 pass/IR 形态（寄存器分配 / 别名 / hoist / alloca 布局）；
3. 核验自举不动点：p.6.10.3 / 6.10.4 后记录新 SHA，确证编译器—运行期配对一致性，必要时按有效对冻结发布编译器；
4. 修复后重跑 §二 证据矩阵（1–8 全绿）与自举 tiec→tiec2→tiec3 不动点一致。

## 七、修复尝试全记录（2026-09-05 深水区 RCA：五变体全数证伪，留行为基线）

> 本轮（RCA-1 已根治表句柄 48B 后）针对剩余「循环体 alloca 动态栈增长 → 0xC00000FD」
> 缺陷族做了系统性多变体实证。**所有「边界化」（hoist/零初始化/stacksave-restore）变换
> 均无法同时满足「探针绿 + 自举真不动点」**，最终代码生成保持 p.6.8 基线（9321B3FA）
> 未动；下述为完整证据（每个变体都经历 tiec→tiec2 自举重建 + 探针 + 自举链验证）。

### 基线（9321B3FA，未改）
* 探针：ed25519/html/probe repro1/repro3 **PASS**；repro2（std/sort 3000 string 冒泡）
  **0xC00000FD**（本缺陷待修形态）。
* 自举：tiec→tiec2→tiec3 真不动点 ✓。

### 变体 A：每函数重建收集数组（= 正确全量提升，即 bc67a3c 已否决方案）
* ed25519/x25519 运行 0xC0000005，自举下一代 tig_read_file AV——已否决（复读历史）。

### 变体 B：选择性提升（入口 + 在环块）+ 入口零初始化（零 store）
* 探针：ed25519 ✓ repro2 ✓ repro1 ✓ html ✓（全绿）。
* 自举：tiec2v1→tiec3v1 哈希不同（fp2v3=False）；tiec3v1 再编译 driver **崩溃**。

### 变体 C：全量提升 + 入口零初始化（最简形态）
* 探针：ed25519 ✓ repro2 ✓ html ✓。
* 自举：tiec2vf→tiec3 哈希不同；**tiec3 连 hello 都无法编译（0xC0000005）**。

### 变体 D：保持原地（in-place）+ 循环边界 llvm.stacksave/stackrestore（逐迭代回收）
* 实现含：CFG 后继/前驱平坦表 + 迭代支配集（位图）+ BFS 自然循环（header 支配 latch）。
* 现象：IR 校验通过（修掉 PHI 块首/SSA 支配/文本序三坑后），但 ed25519 **0xC0000005**
  ——栈址复用使未初始化读从「新鲜新页面（≈0）」变「本调用旧值」→ 依赖方崩溃。

### 变体 E：D + 原地 alloca 后紧跟类型零 store
* 探针：ed25519 ✗、repro2 ✗（0xC0000005，表句柄槽归零后置空读→解引用空指针）、
  html FAIL（行为改变）——最劣变体，弃。

### 根因定性（本轮新增）
* **codebase 存在大量「未初始化读」隐性契约**：编译器自身（tig_read_file/tig_write_file
  块级局部表槽 ats/avs、bOk 分块序列）与 std/ed25519/bigint 等库中，若干 alloca 槽在
  **首次 store 之前被读**，且读取结果参与控制流（如指针槽判空、i8 判真）——历史上依赖
  「逐迭代动态栈分配 = 新页面 ≈0/前帧残留」的非零巧合值运转。
* 任何使槽位复用（hoist 到 entry / stackrestore）的变换，都让「未初始化读」读到**本调用
  前一次写入的旧值**（或显式 0），控制流偏转 → 0xC0000005/行为错误；任何显式归零（零
  store）则直接制造「读取即空指针」，同样崩溃。
* 结论：**该缺陷族的正确修复不在代码生成层，而在 tie 源码层的未初始化读清理**——先对所有
  被读先于写的局部深化一次「首读前必写」规整（或编译器语义层做 definite-assignment 分析），
  再做 hoist 才是语义透明的。推荐路线（按序）：
  1）用「变体 B 全绿、变体 C 可跑」的现状组合做回归基线，逐步为代码库（含 std）中已定位的
  读先于写站点补初始化（最小集：tig_read_file/tig_write_file 块级表槽、ed25519 大循环逐
  迭代槽、sort 冒泡临时串槽）。
  2）每补一处即跑变体 C（全量提升+零初始化）自举链，直到 tiec→tiec2→tiec3 真不动点重建。
  3）届时把变体 C 正式落地，即得「无动态栈分配 + 确定性初始化」的稳健代码生成，p.6.1.7
  家族与 RCA-2 一并闭环。
* 遗留：RCA-2（循环体 alloca 不提升）维持「已 RCA 未根治」状态；本 repo 代码生成保持
  9321B3FA 不动点，与 p.6.8 验收口径一致。

## 九、源码层清理路线·第二轮（2026-09-05）——SSO 假说证伪 + 收集器截断定位 + 零初始化形参撞号修复

> 接 §八 续修。本轮到三件事：崩溃点重审、一个真 bug 的发现与修复（实验内）、
> 以及 v 内部「收集截断」的确定性复现。

* **SSO（短串池）假说证伪**：§八 曾疑崩溃与 tie_sso_alloc 堆分支/SIZE 有关。逐对追踪
  （n≤64 门控）证明 37→100 字符拼接均正常完成（35 对全过）——崩溃实为**编译形态**
  依赖：给 join_lines 内层加 3 行无关键插桩（str_len ×2 + 门控 vc_trace）后，m1
  完整通过、hello/ed25519/html 全绿（编译+运行），且 tiecXdiag 能编译 repro2（opt
  通过）——直接**在活体上复现 §三「同源码仅改变无关邻接代码，产物在崩溃/正常间翻转」**。
* **零初始化形参撞号 bug（实验内发现并已修）**：变体 C 的入口零 store `store T 0, ptr %N`
  中，值为小号 id（`v_a < g_pcnt`）的 alloca 其行内 `%N` 被 renumber 的 `ren_ref` 按

  修复：`v_a >= g_pcnt` 才补零 store。该修复是变体 C 落地前的必要组件（已随实验还原，
  如需落地需重施）。
* **新定位：VC 二代编译器「收集截断」**（tiec2vc 一代 repro2 PASS；tiecXdiag 二代
  repro2 仍 0xC00000FD）：二代生成的 sort_string 仅入口 22 个 alloca 被提升、循环体内
  ~17 个滞留原地；`[HI]` 追踪显示 [lo,hi) 区间（fid=3/4/5 = 427-522/522-618/618-687）

  即编译器内部某访问函数在变体 C 编译下有读先于写，导致生成物里 std/sort 大循环仍
  逐迭代动态栈分配。**与 §七 根因定性一致：剩余未初始化读站点位于编译器自身的
  llvmgen/ir 访问路径内部函数**。
* **下一步（未做）**：在二代二进制内对 `gen_func` 收集循环逐一打点
  `ir.ins_op(ia)`（用文件跟踪），二分到首个「应是 20 实非 20」的 ia，反查 ir 访问链
  （block_func/ins_op 的列表读切），定位后补编译器源码槽位初始化；重施 [形参撞号修复]
  + 该修复，再跑 tiec2→tiec3→tiec4 链至真不动点。已确认该路线可达（探针/ed25519/
  html 全绿的形态存在，缺的只是把收集截断根因清掉）。

## 十、总根因定案与修复（2026-09-05）——表变量赋值引用计数缺 1（真凶，commit 含）

> 三轮深挖后擒获真凶：**`irgen_stmt` 表变量赋值插桩在 store 之后才 load 槽值，
> release 释放的是「新表」而非「旧表」**——retain(新)+1 与 release(读到的新)-1 相抵，
> 新表引用计数缺 1（别名方 `cur = nxt` 仍持有指针）；循环内表变量重入时
> `tig_loopvar_release`（p.6.10.4）将其释放到 0 → 下一轮 `tbl_at` 悬垂读
> （0xC0000005）；旧值（旧 cur）同时泄漏。分配器/编译形态决定「崩 or 恰好续命」——
> 与 §三「产物在崩溃/挂起/正常间翻转」、「§九 加 3 行插桩崩溃消失」完全同构。

* **最小复现（修复前必崩，修复后全过）**：`tests/p617_bisect/m8_noconcat.tie`（3 元素
  join 循环、无拼接——证明与字符串拼接无关，纯表生命周期）；`m4_joinlike.tie`
  （3 元素 + 三段拼接）；`m7_noiter2.tie`（2 元素对照，本来不过崩）；§四 hammer 骨架

## 十三、ed25519 长期泄漏根治：RCA-5/6/7 三处引用计数缺口（2026-09-06，commit 24aaa07）

> §十二 判定的「ed25519 已知限制」**已根治**。变体 C 落地后重审（§十二 所述「irgen
> 支配安全手术」的最小形态即为下述三处 irgen_stmt 改动——变体 C 已把 alloca 全量提升
> 到 entry+零初始化，使「非 entry 表局部」的出口 release 变得支配安全，无需哨兵 select）：

* **根因（三处泄漏，refcount 重建 cd5b86e 后在阶梯上放大为失控）**：

    （invmod 的 m/a/r0/r1/sy0/sy1、divrem 的 qb1/rt 等）从不释放 → ~2.5KB/次。

    持久且入口零初始化，store-null 使上一轮真表引用被**静默丢弃**（refcount 不减）→
    每欧几里得步漏 qx/rem 两表。
  * **RCA-7（主源）**：return 路径对**任何**表返回值无条件 retain，而出口析构只平衡槽持
