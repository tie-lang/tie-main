# 缺陷报告 p.6.1.8：std ext/tls（手写 TLS 1.3/1.2 客户端）对公网真实服务器握手即崩 0xC0000005

> 报告日期：2026-09-05
> 组件：std 网络栈——ext/tls（tls1_3.tie / tls1_2.tie / tls.tie，纯 tie）经 httpc/tls 的公众入口
> 归属仓库：tie-main（本仓库）
> 复现仓库：tie-jcc-core（闭源，证据探针留存；独立三行代码即可复现，见 §四）
> 编号：**p.6.1.8**（正确性模块 p.6.1）
> 严重度：高（std https 对公网不可用；且失败路径无错误返回、直接进程崩溃）
> 状态：未修复
>
> *English summary*: The pure-tie TLS 1.3/1.2 client crashes (0xC0000005) inside
> `tls.connect(host, 443)` against real public servers (e.g. game.gtimg.cn). Plain http
> over the same CDN works (full 22816-byte body), and the same TLS stack passes against
> a local openssl s_server (TLS 1.3/1.2). The crash occurs before `tls.connect` returns,
> with no error sentinel — a public-network TLS handshake compatibility defect in the
> hand-written client, plus a robustness gap (failure must return handle<0, never AV).

## 一、现象

* `tls.connect("game.gtimg.cn", 443)`（以及 `httpc.get_bytes("https://...")` 内部同一路径）→ 进程 **0xC0000005** 直接崩溃；首条日志后即无输出，崩溃发生在 `tls.connect` 内部（未返回）。
* 对比（同程序）：
  * `http://` 明文（`httpc.get_bytes`，net 层）→ 正常，22816 B 完整下载；
  * 本地 `openssl s_server`（TLS 1.3 / 1.2）→ 历史探针（std_httpc_probe 19443/19444）通过。

## 二、证据链（实测，同机，2026-09-05）

| # | 用例 | 结果 |
|---|------|------|
| A | `net.tcp_connect(80)` + 明文 HTTP GET（diag_probe） | OK（200 B 状态响应） |
| B | `httpc.get_bytes("http://game.gtimg.cn/.../s18_head_ornn.png")` | OK（22816 B） |
| C | `tls.connect("game.gtimg.cn", 443)`（tls_diag：首条日志后仅此一路） | **0xC0000005**（崩溃于 connect 内） |
| D | `httpc.get_bytes("https://...")` | 0xC0000005（同 TLS 路径） |
| E | 外部参照：curl / PowerShell 对同一 URL https | 200 正常 |

崩溃路径（tls.connect 内，tls.tie）：

`net.tcp_connect(host, 443)` → `tls13.make_client_hello()` → `net.tcp_send_bytes(ClientHello)` → `tls13.ln(h)`（recv_record）→ `parse_server_hello` / `finish13`（或 1.2 回退路径）。

## 三、根因分析

* 手写纯 tie TLS 1.3/1.2 客户端对**公网服务器握手形态**的兼容性缺陷：
  * 真实服务器（腾讯 CDN 等）ServerHello / 记录分片 / EncryptedExtensions / 证书链（X.509）/ 密钥派生边界的输入形态与本地 openssl 不同 → 解析越界或状态机越界（与已修复 p.6.1.6 str_char 越界同族风险，TLS 报文解析路径同样缺少边界加固）；
  * 或与本仓 § p.6.1.7 编译器代码生成不稳同源（未验证；可用「纯计算不发包」的单测隔离 TLS 逻辑与编译器产物）。
* **健壮性缺口（独立于协议缺陷）**：`tls.connect` 设计上以 `handle<0` 表示失败，但任何握手解析失败都应返回哨兵；当前实测为直接 0xC0000005 进程崩溃 → 标准库对失败无兜底，属不可接受行为。

## 四、最小复现（独立于 jcc，3 行）

```tie
type tie<logic>
import "../../std/tls/tls.tie" as tls   // 或 std/httpc.tie 的 https 入口
func main() {
    var s = tls.connect("game.gtimg.cn", 443)
    println("ok handle=" + to_string(s.handle))
}
```

编译运行即崩（exit 0xC0000005）。任意公网 TLS 1.3 域（如 www.baidu.com:443）预期同类。

## 五、影响

* std https（`httpc` https 入口、`tink` v2 帧加密位/心跳、未来任何公网 TLS 通道）不可用；
* 仅回环/局域网 openssl 形态可用；
* 失败即崩溃会连坐同进程的其他能力（无法降级）。

## 六、修复方向（供 std/后端）

1. 在 `tls13.ln` / `parse_server_hello` / `parse_cert*` 等报文解析路径补边界加固（对照 p.6.1.6 的 pos/blen 修复范式），失败一律走 `handle<0` 返回；
2. 用 wireshark / `openssl s_client` 对照记录流，定位握手不兼容块（首查 ServerHello 扩展与记录分片）；
3. 协议逻辑与编译器产物隔离验证：先以「构造字节直接喂解析函数」的最小单测排除编译器因素；
4. 修复后加入**公网握手回归探针**（对多个公网域做 connect+GET KAT），防止复发。
