# 缺陷报告 p.6.1.8：std ext/tls（手写 TLS 1.3/1.2 客户端）对公网真实服务器握手即崩 0xC0000005

> 报告日期：2026-09-05
> 修复日期：2026-09-06（已修复，见 §七 修复与验证）
> 组件：std 网络栈——ext/tls（tls1_3.tie / tls1_2.tie / tls.tie，纯 tie）经 httpc/tls 的公众入口
> 归属仓库：tie-main（本仓库）
> 复现仓库：tie-jcc-core（闭源，证据探针留存；独立三行代码即可复现，见 §四）
> 编号：**p.6.1.8**（正确性模块 p.6.1）
> 严重度：高（std https 对公网不可用；且失败路径无错误返回、直接进程崩溃）
> 状态：**已修复**（根因=编译器循环内表局部 alloca 未初始化槽 release 垃圾，见 §七）
>
> *English summary*: The pure-tie TLS 1.3/1.2 client crashes (0xC0000005) inside
> `tls.connect(host, 443)` against real public servers (e.g. game.gtimg.cn). Plain http
> over the same CDN works (full 22816-byte body), and the same TLS stack passes against
> a local openssl s_server (TLS 1.3/1.2). The crash occurs before `tls.connect` returns,
> with no error sentinel — a public-network TLS handshake compatibility defect in the
> hand-written client, plus a robustness gap (failure must return handle<0, never AV).
> **Root cause (2026-09-06)**: a compiler codegen defect — loop-local table var allocas
> re-execute per iteration (fresh uninitialized stack slots) while the loopf sentinel
> stays 1, so the 2nd iteration releases a garbage pointer → memory corruption; plus
> struct-field table stores never retained. Fixed in tiec + SNI added to ClientHello.

## 一、现象

* `tls.connect("game.gtimg.cn", 443)`（以及 `httpc.get_bytes("https://...")` 内部同一路径）→ 进程 **0xC0000005** 直接崩溃；首条日志后即无输出，崩溃发生在 `tls.connect` 内部（未返回）。
* 对比（同程序）：
  * `http://` 明文（`httpc.get_bytes`，net 层）→ 正常，22816 B 完整下载；
  * 本地 `openssl s_server`（TLS 1.3 / 1.2）→ 历史探针（std_httpc_probe 19443/19444）通过。

## 二、证据链（实测，同机，2026-09-05）

| # | 用例 | 结果 |
|---|------|------|
| A | `net.tcp_connect(80)` + 明文 HTTP GET（diag_probe） | OK（200 B 状态响应） |
| B | `httpc.get_bytes("http://game.gtimg.cn/.../s18_head_ornn.png")` | OK（22816 B） |
| C | `tls.connect("game.gtimg.cn", 443)`（tls_diag：首条日志后仅此一路） | **0xC0000005**（崩溃于 connect 内） |
| D | `httpc.get_bytes("https://...")` | 0xC0000005（同 TLS 路径） |
| E | 外部参照：curl / PowerShell 对同一 URL https | 200 正常 |

崩溃路径（tls.connect 内，tls.tie）：

`net.tcp_connect(host, 443)` → `tls13.make_client_hello()` → `net.tcp_send_bytes(ClientHello)` → `tls13.ln(h)`（recv_record）→ `parse_server_hello` / `finish13`（或 1.2 回退路径）。

## 三、根因分析（2026-09-05，初判）

* 初判（未定位编译器因素时）：真实服务器握手形态差异 → 解析越界 / 状态机越界；
  或与 p.6.1.7 编译器代码生成不稳同源。
* **健壮性缺口（独立于协议缺陷）**：`tls.connect` 设计上以 `handle<0` 表示失败，但任何握手解析失败都应返回哨兵；当前实测为直接 0xC0000005 进程崩溃 → 标准库对失败无兜底，属不可接受行为。

## 四、最小复现（独立于 jcc，3 行）

```tie
type tie<logic>
import "../../std/tls/tls.tie" as tls   // 或 std/httpc.tie 的 https 入口
func main() {
    var s = tls.connect("game.gtimg.cn", 443)
    println("ok handle=" + to_string(s.handle))
}
```

编译运行即崩（exit 0xC0000005）。任意公网 TLS 1.3 域（如 www.baidu.com:443）预期同类。

## 五、影响

* std https（`httpc` https 入口、`tink` v2 帧加密位/心跳、未来任何公网 TLS 通道）不可用；
* 仅回环/局域网 openssl 形态可用；
* 失败即崩溃会连坐同进程的其他能力（无法降级）。

## 六、修复方向（初版，供 std/后端）

1. 报文解析路径补边界加固，失败一律走 `handle<0` 返回；
2. 用 wireshark / `openssl s_client` 对照记录流定位握手不兼容块；
3. 协议逻辑与编译器产物隔离验证；
4. 修复后加入公网握手回归探针。

## 七、根因定案与修复（2026-09-06）

### 7.1 根因（编译器代码生成缺陷，非 TLS 协议逻辑）

* **现象特征**：TLS 逻辑完全正确——加打印/fs 标记即全流程通过（cloudflare 完整 HTTP 200，
  1.3MB 正文）；去标记即 100% 崩。崩溃点=finish13 flight 内层循环第 2 次迭代的
  `var full/mbody = tbt.sub(...)`；进程以 0xC0000005 **无异常**退出（mini_debugger 抓包：
  仅初始断点 + EXIT 0xC0000005，无 AV 事件）→ 主返回路径被栈/堆破坏。
* **机制**：`tig_loopvar_release`（p.6.10.4）为循环/分支内表变量配**零值全局哨兵**，回边
  重写时 release 槽内「上一轮表」。但 var-decl 的 alloca 生成在 `g_cur_block`（循环体内）——
  回边重执行时**重新分配全新未初始化槽**，而哨兵是全局（跨迭代持久=1）→ 第 2 次迭代
  load 槽读到**栈垃圾** → `tl_tbl$tbl_release(垃圾指针)` 内存破坏。p.6.1.7 的「编译形态
  决定产物生死」同一家族；打印/堆形态可掩盖。`transcript = concat(...)` 赋值路径（p.6.1.7
  已修复）不在此列——崩的是**循环内声明**路径。
* **第二处真实缺陷（同族）**：struct/元组**字段**表赋值从未插桩引用计数——字段只是
  「借用」源局部（TLS Session 填 c_key/c_iv/s_key/s_iv 等字段后，源局部 ca_k 等经出口
  release 计数到 0 → 返回的 Session 字段悬垂 → 应用数据阶段 UAF）。

### 7.2 修复

| 位置 | 改动 |
|------|------|
| compiler/backend/irgen_stmt.tie | 非 entry 块表局部声明在 `tig_loopvar_release` 前先向槽写 null——回边重写读到的「旧值」为 null → 运行时守卫跳过 release（旧表泄漏，本设计普遍接受；杜绝释放垃圾）。**不做全量 alloca 提升**（p.6.1.7 证破坏自举/html/ed25519） |
| compiler/backend/irgen_agg.tie | 字段表赋值补 retain(新)（RHS 直接构造/参数 base 免）；**不 release(旧)**——struct 值复制别名同一表指针，release 旧值提前释放（自举失稳验证） |
| ext/tls/tls1_3.tie + tls1_2.tie | ClientHello 补 server_name（SNI）扩展，`make_client_hello(host)` |
| ext/tls/tls.tie | connect/finish12 传 host；失败路径统一 handle<0 哨兵 |

### 7.3 验证

  服务器策略要求 SNI 证书匹配）/ www.baidu.com **优雅失败哨兵**（handle<0，无崩溃——
  baidu 需 TLS 1.2 P-256 ECDHE，现仅 x25519，列为后续）。
* `tests/tls_probe/https_public_probe.tie`（httpc https 下载）：cloudflare 1,317,458 B /
  bing 70,083 B / github 575,981 B 全量正文正确。
* 既有 tls 探针（gcm/der/chacha_poly/tls_chain/tls13_hello/tls12_hello）全绿；p.6.1.7
  探针（m8_noconcat/hammer_skeleton 10 万次）全过。
* 自举新不动点：tiec（新）== tiec2（fp2==fp3，SHA **ADA0CAB7**）；regress-s21 与基线
  完全一致（99 PASS / 4 已知基线 FAIL / 2 已知 SKIP，无新增失败）。
* 探针留存：tls_public_probe / https_public_probe / field_refcount_probe（字段引用计数验证）。

### 7.4 遗留

* ~~baidu（腾讯系 CDN）需 TLS 1.2 secp256r1(P-256) ECDHE——扩展点（spec 原列为「secp256r1 可选」）~~ **已于 2026-09-06 以纯 tie 方案落地（见 §7.5）**。
* 证书链验签（AC-5）与 CA 内置表仍为既有范围（本修复不涉及）。
* SNI 场景下部分服务器按 SNI 返回不同证书；当前实现不做证书校验，属 AC-5 范畴。

### 7.5 P-256 互通（纯 tie，2026-09-06）

* **背景**：baidu www 端点 TLS 1.2 只支持 secp256r1(P-256) ECDHE、不支持 X25519，且端点不支持 TLS 1.3（openssl 对照：`-groups X25519` → alert 40；`-groups P-256` → 成功；`-tls1_3` → alert 70）。
* **实现**：新增 `ext/tls/p256.tie`（命名空间 p256，纯 tie，std/bigint 底座）——仿射 Weierstrass 点运算（point_double/point_add，λ 斜线公式）、LSB-first double-and-add 标量乘、域求逆用 bigint.invmod；API `keygen/pubkey/dh`（hex IO 对齐 x25519）。`tls1_2.tie` 的 supported_groups 扩为 [x25519, secp256r1]，`parse_ecdhe` 按 group 返回公钥（32B/65B），新增 `gen_p256_sk/derive_shared/cke_pubkey` 按服务器选定 group 分发；`finish12` 双曲线握手。
* **验证**：`tests/tls_probe/p256_ecdh_probe.tie`（openssl 3.6.1 确定性密钥对 + pkeyutl -derive 共享密钥硬编码，pubkey/dh/对称性/篡改拒绝 7 断言全过）；`tls_public_probe` baidu **mode=12 HTTP 200（18798 B）**，其余域（cloudflare/bing/github/microsoft）回归全绿；自举新不动点 tiec==tiec2（SHA 07CC23CF）；regress-s21 与基线一致。
* **注**：仿射每步求逆分支 + std/random 非密码学随机源——本模块定位互通/演示（同 x25519.tie 注记），常数时间与安全随机源列为后续。
